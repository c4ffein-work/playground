## Health check (verified, not just read)

- **Tests**: 175 tests run. 171 pass; the 4 errors are all one environment
  issue (see finding 2) — this container has IPv6 disabled and the server
  cannot create its socket at all here. No product-logic test failures.

  charset is safe in practice.

## Findings

### 1. README says "per-IP" rate limiting; the code is per-client — and failed auth is never throttled
`_check_rate_limit(client["client_id"])` keys the sliding window on client id,
not IP, and the `@_route` wrapper runs auth **before** rate limiting, with
401s returning early. Consequences:

- Unauthenticated requests are completely unthrottled, so credential guessing
  is not rate-limited at all. Secrets generated by the CLI are 64 hex chars so
  brute force is unrealistic, but see finding 3 — custom secrets are accepted.
- All devices sharing one client id share one 30-req/60s window.

Either fix the README (it claims "Per-IP sliding window rate limiting on write
endpoints" in two places) or key the limiter on `client_address[0]` and move
it before auth. An IP-keyed pre-auth limiter would also close the
brute-force gap.

### 2. Server hard-requires IPv6 — cannot start where IPv6 is disabled
`run_server` sets `address_family = AF_INET6` and binds `("::", port)` with a
`IPV6_V6ONLY=0` fallback for v6-only kernels — but there is no fallback for
the opposite case: a host/container where IPv6 is entirely absent
(`socket.socket(AF_INET6)` raises `OSError: [Errno 97]`). This is common in
Docker (ipv6 disabled by default on some setups) and is exactly why 4 tests
error in this session's container. Suggested fix: catch the socket-creation
failure and retry with `AF_INET` / `("0.0.0.0", port)`, logging the downgrade.

### 3. Registration accepts secrets that can never authenticate
`_authenticate` rejects any `client_secret` containing non-hex characters
(`_VALID_SECRET_CHARS`), but neither `/api/clients/register` nor
`server-setup`/`server-add-user`/`register --new-client-secret` validate the
secret's charset. Register a client with a custom secret containing e.g. an
uppercase letter or a dash, and that client is silently locked out forever —
the 401 gives no hint why. Validate secret charset (and a minimum length) at
every registration entry point, mirroring the client_id validation.

### 4. `rotate` failure path tells the user to save a secret it never showed
In `rotate_cmd`, if `_save_secrets` fails after the server has already added
the new token, the message says "Save it manually and run
'companion complete-rotation' to finish" — but the new secret is only emitted
via `logger.debug`, and CLI commands never call `logging.basicConfig` (only
`server --debug` does), so the secret goes nowhere. The stale-rotation 409
recovery path does make this survivable with the old secret, but the message
is misleading. Print the secret to stderr in this path (it's already shown on
success flows elsewhere), or reword the message.

### 5. Minor
- **Client-id timing oracle**: unknown client ids return from `_authenticate`
  before any hashing; known ids cost a SHA-256 + `compare_digest`. Enumeration
  of valid ids by timing is theoretically possible. Hash against a dummy salt
  on the miss path if you care.
- **No Range support on `/download/{id}`**: whole file is buffered and sent in
  one write. Large video preview on iOS Safari generally requires Range
  requests; also each concurrent download duplicates the full file bytes in
  the response path.
- **Pad limit units**: `len(content)` counts characters but the error message
  says bytes; `max_body` caps bytes first for multibyte text. Cosmetic.
- **`sanitize_filename` collisions**: `download <name>` resolves via
  normalized name, first match wins — two files normalizing identically are
  ambiguous. Could prefer exact-name match before normalized match.
- **Python version claims disagree**: README says 3.7+, CI tests 3.8–3.12,
  the pinned-SSL docstring says tested 3.8–3.13. Align (3.7 is untested; the
  `ssl` private-API usage is the risky part on new versions, and CI's matrix
  is the right canary — consider adding 3.13).
- **`build.py` triple-quote fragility**: `index.html` is inlined into a
  `"""…"""` literal; a `"""` sequence or trailing backslash in the HTML would
  corrupt the built file. A `html_content.replace('\\', '\\\\').replace('"""', …)`
  guard — or just base64 like the JS blobs — removes the foot-gun.

## What's good (genuinely)

- The config/state split (declarative read-only config vs server-owned state
  dir) is clean and well documented, and `_json_file_locked`'s
  lock + tempfile + `os.replace` dance is correct, including the
  stale-tmp cleanup and no-write-on-exception behavior.
- Auth design is solid for the stated threat model: salted SHA-256,
  `hmac.compare_digest`, charset pre-validation, and a two-token rotation
  protocol with a thought-through interrupted-rotation recovery story on both
  sides (server 409 handling, `complete-rotation` convergence).
- The paranoid-by-default TLS posture (refuse https without a pin, refuse TLS
  knobs on non-https URLs, fingerprint command requiring `--ca-cert` or
  explicit `--insecure`) is unusually careful for a tool this size.
- The CORS `*` default is fine and the comment justifying it (pure Bearer
  auth, no ambient credentials, so no CSRF surface) is accurate.
- The `@_route` decorator (auth tier, rate limit, body cap, rotation gating in
  one place) keeps 15 endpoints honest with very little repetition.
- Test suite is real: 175 tests covering multipart edge cases, rotation
  interruption, config locking, storage limits, TLS pinning behavior — and CI
  runs it on both the dev and built artifacts across 3 OSes.

## Files persistence (roadmap item) — design sketch

Asked as a follow-up: "what about the files persistence?" Assessment:

Ephemerality is currently a *feature* ("ephemeral by design", files gone on
restart), so persistence must stay opt-in — a `persist-files: true` per-server
config key (or `COMPANION_PERSIST=1`), default off.

The natural shape, reusing patterns the codebase already has:

- **Location**: the state dir, `servers/<name>/files/` — blobs named by
  `file_id` (UUID, never the user filename → no traversal surface), plus a
  `files.json` index holding what `FileEntry` holds minus `content`
  (filename, mimetype, upload_time, client_id, size).
- **Write path**: on upload, write blob via tempfile + `os.replace`, then
  update the index under the same lock+atomic-write discipline as
  `_json_file_locked`. Crash between the two leaves an orphan blob; sweep
  blobs not in the index at startup.
- **Read path**: the big win is to stop keeping bytes in `FILES` at all when
  persisting — store metadata in memory, `open(blob).read()` (or better,
  stream in chunks) on `/download`. Today every file lives in RAM
  (4GB/client cap is a RAM cap!), so disk-backed storage *reduces* memory
  pressure and would pave the way for Range support (the iOS-video issue in
  finding 5).
- **Storage accounting**: sum sizes from the index instead of
  `len(f.content)`.
- **Pad**: trivially persistable with the exact `clients.json` pattern;
  preview state probably shouldn't persist (it's a live-session concept).

Caveats: persistence alone doesn't fix the upload-side RAM spike —
`_read_body` still buffers the whole request to parse multipart; streaming
multipart is a separate, bigger change. And it interacts with two other
roadmap items: file deletion API (needs unlink + index update) and E2E
encryption (orthogonal — server would persist ciphertext).
